ex2 — like button (1 ms ka time-step model; maana: ek viral photo par 10,000 likes/s, saath mein 20,000 feed requests/s,
      app ke paas ek saanjha worker pool, timeout 5 s; har like ek worker pakadta hai jab tak store jawab na de)

1) 10 second, ek viral photo — 1,00,000 likes. Har like ek hi bucket mein: hua / worker na mila / timeout / abhi line mein:
   store, workers, kaun pehle worker le          hua      na mila   timeout   line mein   feed fail    pehla feed fail
   1 row, 2,000, likes pehle                    9,999    88,001         0       2,000    1,96,188    177 ms
   1 row, 2,000, baari-baari                    9,999    88,041         0       1,960    1,76,186    177 ms
   1 row, 2,000, feed pehle                     9,999    88,401         0       1,600           0    —
   1 row, 60,000, likes pehle                   9,999         0    40,002      49,999           0    —
   100 counter rows, 2,000, likes pehle        99,990         0         0          10           0    —
   → Garam row har haal mein ~1,000 likes/s (row ka lock ~1 ms). Baaki asar pool ke niyam par: likes ko pehle worker mile
     toh 177 ms mein pool bhara aur feed gira; feed ko pehle mile toh feed bacha, likes turant mana; 60,000 workers par
     feed bacha par 40,002 likes 5 s baad timeout. Ek saanjha pool ek photo ki dikkat ko poori app mein faila sakta hai —
     likes ko alag pool (bulkhead, lab 39) do. Asli ilaaj store ki raftaar: 100 counter rows par sab theek.

2) Redis jaisa memory counter + har 5 s ek batch write (write coalescing):
   DB par is photo ke writes: 10,000/s → 0.2/s (har 5 s mein ek UPDATE … + delta).
   Keemat: Redis bina persistence ke gire toh aakhri 5 s ke likes ja sakte (is photo ke ~50,000; poore platform par peak par ~8,68,055).

3) Tunnel: reply kho gaya (2%), phone ne same like dobara bheja (seeded, 10 lakh likes):
   asli likes 10,00,000 · counter +1 10,19,823 (2.0% zyada) · set mein user id 10,00,000
   → like ek haalat hai (user ne like kiya ya nahi), event nahi. Set mein dobara daalna kuch nahi badalta — idempotent.

4) Teen regions, ek photo: Tokyo 5,000, Frankfurt 3,000, Virginia 1,000 likes (har like sirf ek region mein gina).
   Regions apni state ki copy bhejte hain; copy der se, ulte kram mein, kabhi do baar pahunchti hai; ant mein sab pahunchti hain (seeded):
   last write wins (poora number)               tokyo 7,012 · frankfurt 7,012 · virginia 7,012
   aaye hue naye likes jodte jao                tokyo 14,336 · frankfurt 14,488 · virginia 11,070
   G-Counter (har region ka slot, merge = max)  tokyo 9,000 · frankfurt 9,000 · virginia 9,000
   → sahi jawab 9,000. G-Counter purani copy, ulte kram aur dohraav ke baad bhi har region par sahi jawab tak pahunchta hai.
   Shart: har like ek hi region mein gina jaaye. Ek user ka like Tokyo mein, retry Frankfurt mein → G-Counter 2,
   user id ka set (union se merge) 1. Unlike ke liye sirf badhne wala counter/set kaafi nahi — OR-Set jaisa CRDT (lab 58).
