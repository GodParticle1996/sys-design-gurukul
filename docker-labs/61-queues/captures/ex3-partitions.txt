A. MODEL (seeded): 1,000 users × 10 events (created → paid → shipped …). 6 partitions, 6 consumers.
   Har consumer apni partition kram se padhta hai. Consumers ki raftaar alag (1–4×, jaise GC ya lag); har event 1–9 ms × raftaar.
   Model maanta hai: har consumer apni partition ka ek event poora karke hi agla leta hai (serial).
   Kya har user ke events usi kram mein khatam hue jismein bane?

key = user id (hash se partition):   0 of 1,000 users ke events ulte kram mein
koi key nahi (round-robin chuna):     1000 of 1,000 users ke events ulte kram mein
→ Kafka kram sirf EK partition ke andar deta hai. Ek user ke saare events ek partition = key do. Key kram ka mauka deti hai;
  partition ke andar parallel handlers, retries ya rebalance ke baad ka purana kaam kram phir tod sakte hain.
  (Kafka Java producer bina key ke round-robin nahi, "sticky" batching karta hai; yahan round-robin sirf tulna ke liye.)

B. Arithmetic: 6 partitions, ek consumer group. Har consumer 100 events/sec.

 3 consumers → 3 kaam par, 0 khaali baithe → 300 events/sec
 6 consumers → 6 kaam par, 0 khaali baithe → 600 events/sec
12 consumers → 6 kaam par, 6 khaali baithe → 600 events/sec
→ Ek group mein partition se zyada consumers bekaar. Parallelism ki chhat = partitions ki ginti.

C. ASLI hash, seeded traffic: 10,000 users, popularity Zipf (s = 1.2). Key = user id. 6 partitions, 10 lakh events.

partition load: 8.4%  31.7%  24.9%  8.7%  11.7%  14.5%
sabse bhari partition = barabar hisse (16.7%) ka 1.90×. Top user akela: 20.8% events.
→ Ek garam key ek hi partition par jaati hai; partitions badhane se garam key nahi bant-ti.

D. ASLI ginti: partitions 6 → 8. Kitni keys nayi partition mein chali gayi? (1 lakh user ids, Kafka murmur2)

75,091 of 1,00,000 keys (75.1%) ki partition badli.
→ Purani partition mein us user ke bina padhe events + nayi partition mein naye events = badlaav ke waqt kram toot sakta hai.
  Isliye partitions shuru mein soch kar rakho (ya badlaav se pehle producers rok kar purane events khatam karo).
